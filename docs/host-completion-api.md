# Host Completion API

ipocket exposes Host-completion reads plus a deterministic operator review
workflow. No LLM is used. Rules are inferred on demand from confirmed active
OS/BMC pairs and stored rejection feedback, so there are no stale learned-rule
counters.

## Current endpoints

Read endpoints are public, consistent with the existing inventory read API, and
do not expose credentials or Host/IP notes. Recording a decision requires an
Editor bearer token. Accepted inventory changes use the normal validated,
audited IP-asset mutation path.

### Read analytics

```http
GET /api/host-completion/analytics
```

The analytics response includes total, complete, and incomplete Host counts.
The incomplete breakdown is mutually exclusive: `os_only` has active OS assets
only, `bmc_only` has active BMC assets only, and `unlinked` has neither active
type linked. Assets without `host_id` do not create a Host or confirmed pair,
but they remain included in `ip_type_counts`.

`confirmed_pairs` counts every OS/BMC address combination on a complete Host. A
Host with two active OS and two active BMC addresses therefore contributes four
pairs while contributing one `complete_hosts` entry. Archived assets are
excluded throughout. `BMC`, `OS`, and `VM` have dedicated type counters; null,
unexpected, `VIP`, and `OTHER` types are grouped as `unknown`.

For valid same-family IP pairs, analytics groups the OS source and BMC target by
their `/16` networks. Replacing the source `/16` with the target `/16` explains
a pair when the remaining address suffix is unchanged. Each returned pattern
reports explained pairs as `support`, same-prefix-group mismatches as
`contradictions`, and `support / confirmed_pairs` as `coverage_percent`.
Patterns with zero support are omitted and results are ordered by descending
support. Invalid or mixed-family addresses still count as confirmed pairs but
are safely omitted from pattern inference.

The React dashboard at `/host-completion/analytics` consumes this endpoint. It
shows completion and incomplete-host charts, IP type distribution, and pattern
confidence. It loads the read-only response on page load and supports a manual
retry after a failed request.

Example response:

```json
{
  "total_hosts": 450,
  "complete_hosts": 310,
  "incomplete_hosts": 140,
  "breakdown": {"os_only": 120, "bmc_only": 15, "unlinked": 5},
  "confirmed_pairs": 310,
  "patterns": [
    {
      "source_prefix": "10.10.0.0/16",
      "target_prefix": "10.30.0.0/16",
      "support": 248,
      "contradictions": 12,
      "coverage_percent": 80.0
    }
  ],
  "ip_type_counts": {"BMC": 310, "OS": 380, "VM": 85, "unknown": 23}
}
```

### List incomplete Hosts

```http
GET /api/host-completion/cases?missing=any&limit=100&cursor=123
```

An incomplete case has exactly one active side of an OS/BMC Host pair:

- one or more active OS assets and no active BMC assets; or
- one or more active BMC assets and no active OS assets.

Hosts with neither type and Hosts that already have both types are excluded.
Archived assets do not contribute to completeness.

Query parameters:

- `missing`: `any` (default), `OS`, or `BMC`;
- `limit`: `1` to `500`, default `100`; and
- `cursor`: return Host IDs greater than this value.

Example response:

```json
{
  "items": [
    {
      "host_id": 42,
      "host_name": "server-42",
      "vendor": "Dell",
      "os_assets": [
        {
          "id": 100,
          "ip_address": "10.10.4.42",
          "project_id": 7,
          "project_name": "payment"
        }
      ],
      "bmc_assets": [],
      "missing": "BMC"
    }
  ],
  "next_cursor": null
}
```

### List confirmed examples

```http
GET /api/host-completion/examples?limit=100&cursor=123
```

This returns Hosts with at least one active OS asset and at least one active BMC
asset. An external pattern-learning Agent can use these shared-`host_id` pairs
as confirmed examples. The endpoint uses the same cursor and limit behavior as
`cases`.

### Get the next review item

```http
GET /api/host-completion/review-queue
```

The engine derives `/16` replacement, `/24` replacement, and exact
single-octet-replacement rules. Identical rules are grouped within the OS source
`/16`. A rule is active when its support reaches
`IPOCKET_HOST_COMPLETION_MIN_SUPPORT` (default `3`). Confirmed pairs in the same
source `/16` that do not match, plus prior rejections generated by the rule, are
contradictions. Confidence is:

```text
min(support / (support + contradictions + 1) + min(support / 20, 0.1), 1.0)
```

The queue includes pairable unlinked OS/BMC assets, unlinked one-sided assets,
and Hosts missing one side. Pair cases appear first, then safe Host suggestions,
then unlinked ASK cases, and finally remaining Host ASK cases. Within each
group the `/16` with the most cases appears first. `NO_BMC` and `NO_OS` exclude
the matching Host-side case; `UNSURE` is stored but may be shown again.

An active rule produces `mode: SUGGEST` only when the candidate is not linked to
another Host, is not an existing asset with a different type, and has not been
rejected for this Host or asset. An existing unlinked expected-type asset is
linked instead of duplicated.
The response includes the candidate, confidence, confirmed-pair evidence, and a
deterministic reason. If no safe active rule remains, the item uses `mode: ASK`.
An empty queue returns `{"item": null, "remaining": 0}`.

### Record a decision

```http
POST /api/host-completion/decisions
Authorization: Bearer <editor-token>
Content-Type: application/json

{
  "case_type": "HOST_MISSING_BMC",
  "host_id": 42,
  "mode": "SUGGEST",
  "os_address": "10.10.4.42",
  "decision": "ACCEPT",
  "candidate_ip": "10.30.4.42"
}
```

Supported decisions are:

- `ACCEPT`: create, restore, or link the candidate as the expected missing asset;
- `CORRECTED`: do the same with a valid `corrected_ip` that is not linked to
  another Host;
- `REJECT`: retain candidate/pair-specific negative feedback;
- `UNSURE`: retain feedback without permanently suppressing the item;
- `NO_BMC` / `NO_OS`: suppress the corresponding Host-side case (and create a
  Host for an unlinked known asset);
- `CREATE_HOST_ONLY`, `ATTACH_EXISTING`, and `DEACTIVATE`: respectively create
  a Host with the selected asset, attach selected assets to `target_host_id`, or
  archive a selected active asset.

Any decision that creates a Host must include a non-empty `host_name`.

Every decision stores the Host, presented mode, candidate/correction values,
decision, deciding User ID, and creation timestamp. `ACCEPT` and `CORRECTED`
also produce the normal IP Asset audit entry. Inventory mutation is completed
before the decision row is returned.

The Editor-only React workflow at `/host-completion/review` uses these two
endpoints to show one queue item at a time. After every decision it reloads the
queue, displays a success or API error notification, and ends with
`No more cases 🎉` when the queue is empty. Decision writes accept either the
normal Editor bearer token or the signed Editor browser session.

## Pagination

Results are ordered by increasing Host ID. When `next_cursor` is not null, pass
that value as `cursor` in the next request. A null value means there is no next
page for the current filter.

## Internal architecture

- `app/routes/api/host_completion.py` defines the HTTP/OpenAPI contract.
- `app/services/host_completion.py` defines the application-service boundary
  and queue/decision orchestration.
- `app/services/host_completion_rules.py` contains the pure deterministic rule
  inference and transformation implementation.
- `app/repository/host_completion.py` performs the inventory queries.

This layering keeps rule calculation unit-testable and keeps asset changes on
the existing validation/audit boundary.
